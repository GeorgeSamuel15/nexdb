You are a senior database systems engineer, distributed systems engineer, storage-engine engineer, TypeScript engineer, Rust engineer, compiler engineer, and software architect.

Build a new project called **NexDB**.

NexDB is a serious relational database management system designed to demonstrate database internals, algorithms, systems programming, storage architecture, transactions, query processing, indexing, concurrency, and reliability.

Do NOT build a simple CRUD application that connects to SQLite, PostgreSQL, MySQL, MongoDB, or another existing database and calls it NexDB.

NexDB must implement its own core database engine.

The first major version should be written primarily in **TypeScript and Node.js** so the architecture and algorithms are easy to understand and develop.

The architecture must be designed so that performance-sensitive components such as storage, indexing, WAL, and concurrency can later be replaced or extended with **Rust** without redesigning the whole system.

The long-term goal is to evolve NexDB into a serious standalone database system capable of being used by other applications.

## Primary Stack

Use:

- TypeScript
- Node.js
- pnpm workspaces
- Zod

For supporting tooling, you may also use:

- Commander.js or a similar CLI framework

- Docker for integration testing and deployment
- GitHub Actions for CI

Do NOT use SQLite, PostgreSQL, MySQL, MongoDB, Redis, Prisma, TypeORM, Sequelize, Drizzle, or another database engine as NexDB's storage engine.

External databases may only be used in optional benchmarking or compatibility tests.

# PHASE 11 — Crash Recovery

Implement crash recovery.

When NexDB starts after an improper shutdown, it should inspect the WAL and recover the database.

Implement a practical recovery mechanism inspired by ARIES.

At minimum support:

- committed transaction redo
- uncommitted transaction undo
- checkpoints
- clean shutdown detection

Create automated crash simulations.

Example test:

1. Start transaction.
2. Modify records.
3. Kill process before commit.
4. Restart NexDB.
5. Verify database consistency.

Also test committed operations surviving crashes.

# Important Engineering Rules

Do not fake features.

Do not put placeholder implementations and call them complete.

Do not claim crash recovery works unless there are tests proving it.

Do not claim transactions are ACID unless the implemented guarantees justify it.

Do not call an in-memory JavaScript Map a persistent index.

Do not hide core database behavior behind third-party database engines.

Do not use ORM libraries to implement the storage engine.

Do not build the UI first.

Do not implement everything inside one application.

Avoid massive files.

Avoid unexplained magic numbers.

Use constants for page layouts and protocol types.

Document binary formats.

Every persisted binary structure must be versioned or designed for future versioning.

# First Major Milestone

The first serious milestone is complete when this workflow actually works:

```bash
nexdb init ./mydb

nexdb ./mydb
```

Then:

```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  username VARCHAR(100) NOT NULL,
  email VARCHAR(255) UNIQUE,
  age INT
);

INSERT INTO users
VALUES (
  1,
  'george',
  'george@nexdb.dev',
  25
);

SELECT *
FROM users
WHERE id = 1;
```

Close NexDB completely.

Restart it.

Run:

```sql
SELECT *
FROM users;
```

The record must still exist.

Then create:

```sql
CREATE INDEX idx_users_email
ON users(email);
```

Restart again.

The index must remain valid.

`EXPLAIN` should show an index scan for:

```sql
SELECT *
FROM users
WHERE email = 'george@nexdb.dev';
```

# Transaction Milestone

This must work:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 500
WHERE id = 1;

UPDATE accounts
SET balance = balance + 500
WHERE id = 2;

COMMIT;
```

If NexDB crashes during the transaction, recovery must leave the database in a valid state.

Also verify:

```sql
BEGIN;

DELETE FROM users
WHERE id = 1;

ROLLBACK;
```

The user must still exist afterward.
